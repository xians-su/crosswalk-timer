# 春樹小幸運

一個手機網頁：打開就知道公司附近三個路口「現在能不能過、還剩幾秒、幾秒後從座位出發剛好」，順便告訴你要不要帶傘。

這份文件寫給接手維護的同事。讀完應該能做到三件事：把它部署起來、知道平常哪些事會自動發生、需要改東西時知道改哪個檔。

## 一、它怎麼運作

沒有後端。頁面打開後，所有倒數都是手機用自己的時鐘、對照一份時刻表算出來的。

| 東西 | 來源 | 多久更新 |
|---|---|---|
| 紅綠燈時刻表 `schedule.json` | 臺北市交通管制工程處公開的「路口號誌時制計畫」PDF，由 `parse_plan.py` 解析、`build.py` 產生 | 每天自動重抓比對 |
| 時刻表的校正 `calib.json` | 用公開的路口攝影機實際看燈號，和時刻表比對 | 每天三次，另外每週把各時段掃一遍 |
| 帶傘判斷 | 中央氣象署雷達一小時降雨預報（免金鑰），頁面直接查 | 頁面每 5 分鐘查一次 |
| 雨量站、天氣特報、氣溫 | 中央氣象署開放資料 API（要金鑰，見第六節） | 同上 |

臺北市沒有公開的即時燈號 API。這個工具能準，是因為這幾個路口的號誌照固定時制表運作，而且每一輪的起點可以從午夜推算。這個前提如果變了（例如路口改成動態控制），工具就會不準，見第七節。

## 三、部署

需要的只有一個能放靜態檔案的地方，和一個能跑排程的地方。最省事的組合是 GitHub：

1. 在公司的 GitHub 帳號或組織下建一個 **公開** 的 repo，把這個資料夾的內容推上去。公開 repo 的排程不計費；私人 repo 每月約會用掉 1,100 分鐘的 Actions 額度。
2. repo 的 Settings → Pages，來源選 `main` 分支的根目錄。網址會是 `https://<帳號>.github.io/<repo 名稱>/`。
3. repo 的 Settings → Actions → General，確認 Workflow permissions 是 Read and write。兩個排程會把更新後的檔案直接 commit 回 `main`。
4. 到 Actions 分頁手動各跑一次 `official-plan` 和 `camera-check`，確認都是綠的。

要用公司自己的網域或主機也可以，只要把這五個檔放上去並定期從 repo 同步：`index.html`、`schedule.json`、`sw.js`、`icon.png`、`favicon.png`。（`icon-512.png` 是備用的大尺寸圖示，頁面目前沒有用到。）頁面用相對路徑讀 `schedule.json`，所以兩者要放在同一個資料夾。

本機預覽：在資料夾裡執行 `python3 -m http.server`，開 `http://localhost:8000/`。

本機要跑腳本的話需要 Python 3.10 以上，以及：

- `parse_plan.py`：系統要裝 `pdftotext`（Debian／Ubuntu 是 `poppler-utils` 套件，macOS 是 `brew install poppler`）
- `logger.py`、`check.py`：`pip install opencv-python-headless numpy`
- `make_icon.py`：`pip install Pillow`

腳本在 Linux 上測過，沒有在 Windows 上測過。

## 四、平常會自動發生的事

- **每天 03:10**：重抓三個路口的官方 PDF 並重建時刻表。任何一個路口的時制內容有變（時段表、週期、時差、時相秒數），攝影機修正就歸零，因為舊修正對新時制不適用；官方只更新了資料時間則不會歸零。
- **每天 09:00、11:40、15:00**，以及**每週三、六把每個時段各查一次**（週三查平日的 9 套時制、週六查假日的 8 套）：從攝影機取樣 13 分鐘（每秒 10 張），看赤峰街口和中山站 3・4 號出口各一顆燈和時刻表差多少。量測解析度 0.1 秒。每天那三次是因為實際使用集中在 09:00–18:00。每次抽查會從市府的攝影機伺服器下載約 90 MB 的影像，一週 38 次約 3.5 GB，所以不要排得更密。
  - 差距在 1 秒內：記一筆「ok」。
  - 差超過 1 秒，而且至少 4 輪一致、各輪之間相差不到 0.6 秒：自動修正那個路口那一套時制（記為「adjusted」，修正到 0.1 秒）。頁面幾分鐘內就會跟上。
  - 差超過 1 秒但證據不夠：記一筆「drift」，不動時刻表，排程以失敗結束，GitHub 寄信通知。
  - 燈讀得很清楚但燈號長度或週期對不上：記一筆「mismatch」；如果是赤峰街口，排程以失敗結束。
- 承德路口不在抽查裡，原因見第七節。

所以號誌如果慢慢漂掉，白天的時段最慢隔天會被量到，其他時段最慢一週：漂得夠明確就自動修正，不夠明確就寄信。頁面本身不會累積誤差，它每秒都用絕對時間重算。

需要人處理的只有兩種信：

| 收到的信 | 意思 | 怎麼辦 |
|---|---|---|
| `official-plan` 失敗 | 官方 PDF 的版面變了，或某個路口的時相數量和 `crossings.json` 寫的不一樣 | 看 log 裡 `assert` 的訊息，對照 PDF 修 `parse_plan.py` 或 `crossings.json` |
| `camera-check` 失敗 | 某顆燈和時刻表差超過 1 秒但沒有被自動修正（drift），或赤峰街口的燈號長度對不上（mismatch）；也可能是攝影機網址換了、鏡頭被轉動 | 看 `checks.json` 最後幾筆的 `status` 和 `err`。偶爾一次 drift 可以先觀察隔天；連續幾天同一套時制都 drift，就照 `err` 手動改 `calib.json`。若是 `logger.py` 連不上，見第五節「攝影機」 |

GitHub 的排程偶爾會延遲幾十分鐘，甚至整班沒跑（2026-11-18 就發生過一次）。白天那三次漏一班隔天會補上，每週那一輪漏掉的要等下週；如果發現連續好幾天都沒有新的抽查紀錄（頁尾「最近」的時間停住），或是希望抽查準時跑，可以在自己的主機上用排程在同樣的時刻執行 `gh workflow run camera-check`。這樣不會重複：排程啟動的那一次發現 50 分鐘內已經有別的抽查，就會自己跳過（`check.yml` 的第一步）。

## 五、常見的修改

### 改名稱、預設走路秒數

改 `crossings.json` 的 `name`、`dir`（名稱旁的小字）、`default_walk`，然後執行 `python3 build.py`。

### 加一個路口

先確認本機裝了 `pdftotext`（見第三節）。

1. 找到路口的官方代碼。臺北市資料大平臺的「臺北市路口號誌時制計畫」有一份路口清單 CSV，裡面有名稱、座標、代碼（例如 `SLWH710`）。
2. 下載它的時制表 `https://www.ttcx.dot.gov.taipei/cpt/api/TimingPlan/pdf/<代碼>` 來看。
3. 判斷行人走的是哪個時相。PDF 每個時制下面有一列四個數字一組的參數，順序是「黃、全紅、行人閃、行人停」。行人閃不為 0 的時相才有行人號誌；要判斷哪個時相對應哪個方向，看 PDF 下方的分相圖，或像現有三個路口一樣用攝影機對照。
4. 在 `crossings.json` 加一筆：

   | 欄位 | 意思 |
   |---|---|
   | `id` | 英文代號，頁面用來存每個人的設定，定了就不要改 |
   | `code`、`name`、`full`、`dir` | 官方代碼、卡片名稱、頁尾的官方名稱、名稱旁的小字 |
   | `phases` | 這個路口的時制可能有幾個時相，例如 `[3]` 或 `[4, 6]`。解析時用來檢查 |
   | `walk_phase` | 行人走第幾個時相，從 0 算起。不同時相型態不一樣時寫成對照表，例如 `{"60": 2, "A9": 4}`。鍵是時相型態代碼：PDF 右半邊每套時制那一列，依序是「時制、週期、時差、方向、時相」，「時相」那一欄的兩碼（例如 `60`、`A9`、`CF`、`12`、`AD`）就是它；解析後也會存在 `plans.json` 每套時制的 `type` |
   | `min_clear` | 可過時間至少要扣掉的秒數（實際扣的是「行人停」和它之中較大的） |
   | `default_walk` | 預設從座位走到路口的秒數 |
   | `options` | 選填。同一個路口有兩個橫越方向時用，頁面會出現切換鈕。寫法看承德路口那筆 |

5. 執行 `python3 parse_plan.py` 和 `python3 build.py`。

要讓新路口也被攝影機抽查，再加一個 `lamp` 欄位：`roi` 是 `logger.py` 的哪個取樣框、`color` 是看紅燈還是綠燈亮起、`lead` 是燈號變化比行人可過早幾秒、`len_phases` 和 `len_extra` 用來算這顆燈該亮多久（哪幾個時相的秒數相加再加幾秒）、`len_tol` 是長度容許差幾秒、`adjust` 決定允不允許自動修正、`strict` 決定燈號長度對不上時要不要讓排程失敗。這些數字要先用攝影機實際量過再填，現有三筆可以當範例。

### 改版面、文字、顏色

都在 `index.html`。顏色集中在最上面 `:root` 的變數，淺色和深色各一組。

### 改圖示

改 `make_icon.py` 後執行它，再把 `index.html` 裡 `icon.png?v=7` 的數字加一，iPhone 才會重新抓。已經加到主畫面的人要刪掉重加才會看到新圖示。

### 攝影機

攝影機是臺北市交控中心 415 號（承德路一段與南京西路口），串流網址寫在兩個地方：`logger.py` 最上面的 `B`（不含結尾的 `/live.m3u8`），以及 `index.html` 裡的 `CAM`（頁面上「路口即時影像」用的，含 `/live.m3u8`）。

網址中間那串代碼可能會換。換了之後，到任何一個列出臺北市路口即時影像的網站打開 415 號攝影機那一頁，檢視網頁原始碼搜尋 `live.m3u8`，就是新的網址，兩個地方都要改。

`logger.py` 有三種用法：`logger.py 分鐘 輸出檔` 是細取樣（每秒 10 張，排程用這個）；後面再加 `coarse` 是每秒 1 張，對攝影機伺服器的負擔小，適合連續記錄好幾天；不帶參數則是每秒 1 張並存截圖，找取樣框位置時用。

`ROIS` 是五個取樣框的位置，對照圖在 `docs/camera-lamps.jpg`：

| 框 | 是哪顆燈 |
|---|---|
| A | 南京西路在 25 巷口的燈（中山站 3・4 號出口） |
| B | 南京西路在赤峰街口的燈 |
| C、D、E | 承德路口南京西路方向的燈群附近（目前沒有用在抽查上） |

鏡頭如果被轉動，這些框要重新定位：用 `logger.py` 不帶參數跑幾分鐘，它會在 `data/` 留下截圖，從截圖找出燈的像素位置。

## 六、氣象資料與金鑰

- **不用金鑰就有的**：帶傘結論。頁面直接讀氣象署放在公開儲存空間的雷達降雨格點檔，只抓路口周邊九格。
- **要金鑰才有的**：附近雨量站的實測雨量、天氣特報、臺北站的氣溫與紫外線、大同區降雨機率。

金鑰不放在 repo 裡，也不寫進頁面。每個人到中央氣象署開放資料平臺免費註冊、取得自己的授權碼，然後用下面這個網址開一次，金鑰就會存在那支手機上：

```
https://<你的網址>/#cwa=<你的授權碼>
```

這個連結含金鑰，不要轉傳。沒有金鑰的人看到的氣溫等數字來自 Open-Meteo 的模型預報。

空氣品質也來自 Open-Meteo（模型推估，不是測站實測），不用金鑰。AQI 超過 100 時在帶傘那一條提醒敏感族群戴口罩，超過 150 時提醒所有人；平常只在「天氣細節」裡看得到數值。環境部的測站資料比較準，但它的 API 要金鑰、而且不允許網頁直接呼叫，要用的話得另外加一支排程代為查詢。

## 七、準確度：目標、算法、已知限制

目標是赤峰街口和中山站 3・4 號出口的倒數誤差維持在 1 秒內。這一節說明靠什麼達成、哪些地方做不到。

### 時刻表怎麼算

每一套時制有三個數字：週期、時差、各時相秒數。

- 一輪的起點＝當天午夜起算的秒數減掉時差後，能被週期整除的時刻。目前用到的週期（90、120、150、180、200 秒）都能整除一天，所以每天午夜自動對齊。`build.py` 會檢查這一點，遇到不能整除的週期會直接報錯。
- 各時相依序排列。行人可過的時段從 `walk_phase` 那個時相開始，長度是該時相秒數減掉「行人停」。
- `calib.json` 依路口代碼分開存，每個路口的 `K` 和 `per_plan` 是攝影機量到的偏移（可到 0.1 秒），加在起點上；`checked` 記錄哪些時制核對過；只有每秒 10 張的細取樣抽查才算數（粗取樣只能確認到 3 秒，不計入）。目前偏移都是 0。

### 誤差從哪裡來，各自怎麼處理

| 來源 | 大小 | 處理方式 |
|---|---|---|
| 號誌本身每一輪的抖動 | 赤峰街口 0.05 秒、中山站 0.09 秒（2026-11-18 以每秒 10 張實測 7 輪） | 不用處理，這兩個路口是定時號誌 |
| 時刻表的偏移 | 同一次實測為 +0.35 到 +0.5 秒，其中包含影像串流延遲 | 每天三次加每週一輪抽查；超過 1 秒且證據充分時自動修正 |
| 使用者手機的時鐘 | 常見零點幾秒，偶爾超過 1 秒 | 頁面向伺服器對時後修正（見下） |
| 倒數換數字的時機 | 原本最多晚 1 秒 | 頁面在燈號該跳的那一瞬間重畫 |
| 換時制的過渡 | 2026-11-18 20:00 和 23:00 實測（兩個路口、兩次一致）：舊時制把進行中的那一輪跑完，夾一個過渡輪，從新時制的第二輪起完全照新時制走。不照這個規律算的話最多差 47 秒 | 頁面的 `windows()` 照這個規律算。**過渡輪做不到 1 秒內**：它的長短抓不準，實測和算法差過 5、9、21 秒，所以那一輪把數字變淡、標示「換時制中，這一輪抓不準」，也不列進可預約的時刻；前後各輪照常。2026-11-20 補上一條：過渡輪其實是新時制的一輪、只是前段被縮短，所以舊的一輪跑完到新時制的「可以過」之間隔 75 秒以上時（頁面的 `GAP_MIN`），過渡輪裡照新時制的位置會有一班，頁面會列出來。平日 17:00 兩個路口都是這種情況（17:04 那一班，兩天的記錄都準時），原本頁面漏掉它、要人多等一輪。隔 7、29、54 秒的幾次都沒有出現，所以不列。`python3 transitions.py 記錄檔` 可以對任何攝影機記錄重新驗證這條規律 |
| 行人燈和車道燈的時間差 | 赤峰街口現場對過一次，差 0.5 秒；中山站未知 | 攝影機看得到的是車道燈，行人燈的秒數照官方表推算。只能靠人在現場對時確認（見下） |
| 影像串流的延遲 | 假設 0.3 秒，實際不確定約 ±0.3 秒 | `check.py` 的 `FINE['bias']`。現場對時後可以把它定下來 |

### 手機時鐘修正

頁面每次開啟會向放頁面的伺服器發三次很小的請求，讀回應標頭 `X-Time`（伺服器時間，秒，含毫秒），取來回最快的一次算出手機時鐘差多少，之後所有倒數都用修正後的時間。Setting →「一般」→ 校正那組會顯示結果。

伺服器要自己加這個標頭，nginx 的寫法是 `add_header X-Time $msec always;`。沒有這個標頭的主機（例如 GitHub Pages）頁面照常運作，只是不修正手機時鐘。伺服器本身的時鐘要有對時。

### 現場對時

人在路口時，展開那個路口，在行人綠燈亮起的瞬間按 Setting →「一般」→「行人綠燈剛亮」。按鈕下面會寫「你剛才按的比時刻表晚 1.3 秒；最近 3 次平均晚 1.1 秒」。這是唯一能取得行人燈絕對時間的方法。多按幾輪取平均，把數字寫進 `calib.json` 那個路口的 `K`（正值代表實際比時刻表晚），再跑 `python3 build.py`。

手按本身大約有半秒誤差，所以這一按和時刻表差不到 1 秒時，頁面會維持用時刻表（按鈕下面寫「差不到 1 秒，照時刻表走」），差 1 秒以上才改用那一按。

目前的現場紀錄：2026-11-19 09:14 在赤峰街口按過一次（平日 07:00–09:30 那套時制），和時刻表差 0.5 秒；同一套時制當天 09:00 攝影機量到 −0.04 秒，兩邊一致。中山站 3・4 號出口還沒有人在現場對過。

### 其他已知限制

- **承德路口每一輪都不固定**。同一次實測的 7 輪裡，南京西路在這個路口的綠燈有時準時、有時提早 5 秒、有時提早 10 秒，結束時間也會提早 5 秒。所以這個路口：可過時間多扣 6 秒（`crossings.json` 的 `shorten`）、頁面標示「估計值」、不納入攝影機抽查。它不可能做到 1 秒內。
- **中山站 3・4 號出口不是 `strict`**：它可以自動修正（`adjust`），但它的燈號長度規則還沒有在所有時制上驗過，長度對不上時只記錄、不讓排程失敗。觀察幾週沒有誤報後可以改成 `strict`。
- **交接時攝影機修正和抽查紀錄已歸零**，所以頁面最下方會從「攝影機已核對 0/24 套時制」開始（兩個路口各 12 套），隨每天的排程陸續累積，後面會帶最近一次核對的日期時間（例如「・最近 11-19 11:40」）；日期停在很久以前，就表示抽查沒在跑。交接前（2026-11-18）兩個路口的平日 17–20 時和 20–23 時兩套只用粗取樣對過（3 秒內），不算達到 1 秒標準；平日白天 09:30–13:00、13:00–17:00 兩套要等排程抽查才有紀錄。
- **攝影機看到的是車道燈，不是行人燈**，見上表。
- **官方說有 361 個路口採用即時調整秒數的動態控制，名單未公開**。赤峰街口和中山站目前觀察到的週期完全固定，但如果哪天被納入，時刻表就會失準，`camera-check` 會開始出現 drift 或失敗。
- 交警手動指揮、號誌故障、臨時改秒數，頁面都不會知道。
- 頁面裡有幾個自訂的門檻，沒有官方依據：雷達預估的一小時雨量換成口語時，不到 0.5 毫米叫毛毛雨（只說「建議帶傘」）、5 以下小雨、15 以下中雨、以上大雨，0.5 毫米以上才說「要帶傘」；帶傘結論下面那一行，紫外線指數 6 以上、風速每秒 8 公尺以上才會提到（收合的「天氣細節」裡則一律顯示）。另外，不會下雨但紫外線指數 8（過量級）以上時，大字會改成「建議遮陽」。都在 `index.html` 裡。

## 八、流量與耗電

頁面刻意省流量和電，改動時請維持：

- 畫面每秒重畫一次，頁面在背景時完全不畫。
- 氣象資料每 10 分鐘才查一次（資料本身就是 10 分鐘更新），頁面在背景時不查；預報、特報、空氣品質 15 到 30 分鐘內重複使用。
- 雷達降雨格點只抓路口周邊九格，每個檔三個 32 位元組的小請求，不下載整份 2.7 MB 的檔案。
- 時刻表用條件式請求，沒變就只回一個標頭，而且最多 30 分鐘問一次。
- 雷達圖（約 1 MB）和即時影像只在使用者點開時才載入，收合或切到背景就停。
- 「螢幕保持亮著」很耗電，預設關閉，在 Setting 的「一般」裡才能打開。

2026-11-18 實測：每 10 分鐘一輪的氣象更新約 6 KB，一小時不到 40 KB。

## 九、使用者的設定存在哪

每個人的設定存在自己手機的瀏覽器裡（`localStorage`，鍵名以 `xw_` 開頭）：哪張卡片展開、路口的排列順序、各路口的走路秒數、微調秒數、深淺色、氣象署金鑰、Memo 的文字與開關（Memo 預設關閉，在Setting 的「一般」裡打開），以及在「之後可以過」點選的那一班（點了之後，這張卡片展開和收合時的倒數與出發時間都改成對那一班；按「回到即時」或那一班開始時自動取消）。換網址、清除網站資料、或刪掉主畫面圖示重加，設定都會歸零。

這些資料只留在各自的手機上，頁面不會把它們傳到任何伺服器，維護的人看不到任何使用者的設定或備忘內容。

## 十、測試

改完東西先跑測試，三支加起來不到兩分鐘：

```
bash tests/run.sh
```

| 測試 | 驗什麼 | 需要 |
|---|---|---|
| `tests/logic.test.mjs` | 時刻表與天氣的計算：每個路口全天有沒有涵蓋、平假日與時段有沒有選對、能不能過與何時出發、未來 30 分鐘的時刻（含跨時段）、雨量用語、紫外線與空氣品質分級 | Node 18 以上 |
| `tests/check.test.sh` | 攝影機核對本身會不會判斷：用一段錄好的細取樣（`tests/sample-fine.csv`，2026-11-18 週三 22:36 起 14 分鐘，每秒 10 張），真的時刻表要判「吻合」且誤差在 1 秒內、故意偏 30 秒和只偏 1.5 秒都要被抓到、燈號長度不對要以失敗結束；最後從一份故意寫錯的時刻表出發，讓它自己修正、重建，再量一次要回到 0.3 秒內 | Python、numpy |
| `tests/page.test.py` | 在瀏覽器裡實際操作頁面：兩種寬度不會橫向捲動、卡片開合、各路口的走路秒數、預約某一班與回到即時、換方向、Memo 開關與清除、深淺色、下拉重整、拖曳改順序、重開後設定還在、沒有網路也開得起來 | `pip install playwright`，再執行 `playwright install webkit chromium` |

`page.test.py` 會自己起一個本機伺服器，並擋掉所有對外連線，所以不會真的去查天氣或攝影機。

兩個會讓測試「合理地」失敗的情況：

- 官方時制表改版後，`check.test.sh` 用的那段錄影就對不上新的時刻表。用 `python3 logger.py 14 tests/sample-fine.csv` 重錄一段，並把測試開頭註解裡的日期時間改掉。
- `logic.test.mjs` 是直接從 `index.html` 裡擷取函式來跑的，靠的是函式名稱。改了函式名稱或搬動順序，測試會說「cannot find …」，照訊息調整測試檔開頭的擷取清單。
